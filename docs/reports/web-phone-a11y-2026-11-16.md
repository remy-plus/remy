# Web app: phone width and accessibility, finishing pass, 2026-11-16

Target: every screen works at 390x844 and 1440x900, with a keyboard only and with a screen reader, to WCAG 2.2 AA. Yesterday's pass (touch targets, composer above the keyboard, one throttled spoken status line, focus kept when an opener goes away, field-edge contrast, tab titles, reduced motion in chat scroll) was already on main. The unsaved edits that helper left in its worktree were lost, so this pass started from the screens, not from those edits.

## Method

The app ran in mock mode (`?mock=1`, `pnpm --filter ./apps/web dev`) and was driven in headless Google Chrome through `playwright-core` (already a dependency of `packages/browser`; nothing added to the repo). Scripts were kept outside the repo. Touch emulation on at phone sizes. Sizes: 390x844, 1440x900, and 320x568 for reflow.

For 28 routes at each size the scripts measured: page overflow, elements outside the viewport, controls under 44 px (touch) with no name, heading order, console errors. They also tabbed through 70 stops per route (focus ring present, not covered, not off-screen), opened every dialog (focus in, Tab and Shift+Tab, Esc, focus returned), computed contrast of every text node against its real background, listed live regions, and injected the WCAG 1.4.12 text spacing. Screenshots were read for every screen at 390 and for the main ones at 320 and 1440.

## Checked and found fine (no change)

- No horizontal overflow, no element outside the viewport, no unnamed control, one h1 and no skipped heading level, on all 28 routes at 390, 320 and 1440. Switches draw 40x24 and have a 44 px hit area.
- Touch targets in all dialogs on touch (44 px); on mouse they are 28 to 39 px, which is allowed.
- Colour: every text node on every route is at or above 4.5:1 (3:1 for large text) except disabled controls (exempt) and the hover-revealed Copy button while hidden. Ink, paper and stone are used as in the brand guide; the accent is only on the cursor, done marks and switches.
- Dialogs (dock sheet, History, command palette, approval, confirm): native `<dialog>` with a name, focus moves in, Tab stays in, Esc closes, focus returns to the opener. In the approval card Esc means "Not now" and focus moves to the confirmation.
- Reduced motion: one global `prefers-reduced-motion` rule, the caret, the orb, and scripted scrolls honour it.
- Text spacing (1.4.12): nothing is clipped on any screen; only `sr-only` elements report overflow.
- Streaming answer: the visible text is hidden from assistive tech while it is written, one polite line says "Remy is writing the answer", and the finished answer is read once.

## Real browser vs tests only

Checked in headless Chrome (mock data): everything in the tables above, at 390x844, 320x568 and 1440x900, with screenshots read; focus order and rings; all dialogs; computed contrast; live regions listed; text spacing; the first-run key form with an empty key, a key accepted by the mock, and sign-in with an empty, a wrong and an expired one-time code; a chat turn ("ramen nearby") start to finish; the three phone jumps (Brain, Skills, Connections) after the change.

Only in tests (jsdom): focus return after errors, `preventScroll` on the approval button, the jump buttons' calls (matchMedia stubbed), the single spoken save, `aria-pressed` on Find a skill, the CSS guards (skip link, `dvh`, `scroll-padding`).

Not checked at all:

- The location notice in chat: the mock has no location prompt, and headless Chrome has no permission prompt. Its markup (a polite status line above the composer) is covered by the existing `location.test.tsx` and was read, not seen.
- The real `remy serve` server and the one-time sign-in link against it (only the mock's answers were used).
- The voice overlay (headless Chrome has no microphone), a screen reader (VoiceOver, TalkBack), a real phone: iOS zoom-on-focus, the keyboard covering the composer, safe-area insets, landscape.
- A browser's own focus handling for native dialogs outside Chrome (Safari, Firefox).

## Left

- The command palette takes Tab for "tell Remy to do it" (a documented design choice), so Tab does not move between its parts. Arrow keys and Esc work. It is worth deciding whether that is wanted for keyboard-only users.
- Esc in the approval card declines, as designed. A keyboard user who presses it by habit declines the action (it says so on screen and moves focus to the answer).
- The palette footer lists keyboard keys on a phone.
- There is no favicon (Chrome logs a 404 for `/favicon.ico`).
- The Settings section list takes about 280 px of a phone's first screen before the section title.
