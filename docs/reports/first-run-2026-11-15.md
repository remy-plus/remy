# First run, walked for real (2026-11-15)

Goal: a person who installs Remy and runs `remy serve --open` gets from nothing to a first good answer in the browser in under two minutes, without the terminal after that first command and without reading docs.

How it was walked: a fresh `REMY_HOME` in a temp folder, `REMY_KEYCHAIN=off`, no key anywhere, the real server from source (`remy serve`) under a pseudo-terminal so it prints what a person sees, the real web build in a browser, and a fake OpenAI-compatible provider on a local port (a small `node:http` script; a one-line `--import` preload sent `https://api.openai.com/` to it). No paid call was made and the real `~/.remy` and Keychain were not touched. Timings are machine time against a fake provider; human time is estimated and says so.

## Before (the code at the start of this branch)

| # | Step | What the person sees | Result |
| - | ---- | -------------------- | ------ |
| 1 | `remy serve` in a terminal, no model set up | `Remy needs a model first. Run remy login to connect one, or set REMY_PROFILE and REMY_MODEL.` then the shell prompt (about 6.7 s including pnpm start-up) | **Blocked.** The server exits before it opens a port, so there is no browser and no sign-in link. |
| 2 | Run `remy login` in the terminal | A terminal picker with 20 providers, a key prompt | The person must find the right provider and know what an API key is, in a terminal. |
| 3 | Run `remy serve` again | A raw token, then `That is your token. It is shown once. Send it as: Authorization: Bearer <token>`, `remy serve listens on …`, `To sign in on this machine, open this link (it works once, for 10 minutes):` and the link | API jargon before the one thing a first visit needs. |
| 4 | Open the link | `Good evening` / `What do you need?`, an input, four suggestions (one is "Summarise the files in my Documents folder", which needs a folder set in Settings) | Nothing says whether Remy has a model. |

With only the server fixed (to see what the old web app did with no model, which is what the first half of this branch exposes), I typed "What can you do?" and pressed Enter. The only feedback was one line under the box: `Remy needs a model before it can answer. Add a key to get started.` There was no way to add a key in the browser. The old welcome screen (reachable only by hand) said `Run that in your terminal. The key goes in the Keychain on this computer, and this page never sees it.`, and Settings said `To change which provider Remy uses, run remy login on that machine.`

So: three terminal steps, two commands the person has to know, and a dead end if they started with the browser.

## After

| # | Step | What the person sees | Machine time |
| - | ---- | -------------------- | ------------ |
| 1 | `remy serve --open` (README quick start) | The terminal prints the access token once, then `That is your access token, for other devices and scripts. Machine time from a cold server to the first answer was 0.34 s against the fake provider; a real provider adds one to three seconds for the key check and the first answer. The human time is dominated by getting a key from the provider's site (the step no product can remove), which is why that page is linked and named in the form. Everything else is two clicks, one paste and one click, so the path fits well inside two minutes for a person who has a key. I did not time a person.

After a restart of the server (same `REMY_HOME`), `GET /api/setup/model` says `ready: true` with OpenAI and `gpt-5-nano`, and Settings shows the provider as in use: the key persisted and the browser was not asked again.

Files after the walk: `credentials.json` and `logins.json` are mode 0600; the key appears in `credentials.json` only (the Keychain is off in this walk), not in the event database, the chat file, the sign-in files or the terminal output.

## What changed

- **`remy serve` starts with no model** (`apps/cli/src/model-slot.ts`, `cli.ts`). A swappable model slot is handed to the runtime. Empty, it answers like a model that cannot be reached, so a task resumed before a key exists pauses and keeps its place instead of failing. New tasks get `409 Remy needs a model before it can answer. Add a key to get started.`
- **`GET`/`POST /api/setup/model`** (`apps/cli/src/serve-model-setup.ts`). The short list, cheapest first by the built-in price table, and the save. See the security notes in the final report.
- **The web app** asks once, on the front door only, whether Remy has a model and goes to setup if not. The setup screen has two steps; `ModelKeyForm` is shared with Settings, Model and keys. All errors come from the server's own sentence (`describeError` already prefers it), or the existing offline sentence.
- **README and `docs/home-server.md`** say `remy serve --open` and nothing else for the first run; the terminal prints plain words.

## Left

- The provider order is by price in the built-in table (OpenAI `gpt-5-nano` first). Haiku 5.5 is the model this repo has proven most on live suites; moving Anthropic first is one array in `serve-model-setup.ts` if the owner prefers it.
- A custom base URL and the other 15 providers are terminal-only on purpose (a browser-supplied address would let the key be sent anywhere).
- The home page's own suggestions still include "Summarise the files in my Documents folder", which needs a folder in Settings. The first-run page does not use it.
- Switching the model from Settings while a task runs changes the model for that task's next step. It works, and costs are priced by the model used, but it is not tested for a task in flight.
- No real provider, no real Keychain and no real browser-opened window (`--open` is covered by an existing test with a fake opener) were used.
